## 2. 多租户架构设计（核心难点）

### 2.1 为什么多租户？
SaaS 产品必须隔离客户数据，同时让基础设施共享降成本。

### 2.2 租户隔离策略

| 方案 | 隔离级别 | 成本 | 适用场景 | 我们选 |
|------|----------|------|----------|--------|
| 独立数据库 | 强 | 高 | 大客户 / 数据合规极严 | ❌ 成本高 |
| 独立 Schema | 中 | 中 | 中大型客户 | ❌ 运维复杂 |
| 共享数据库 + 租户 ID | 弱 | 低 | 中小客户 SaaS | ✅ **选这个** |
| 混合（大客户独立 DB，小客户共享） | 灵活 | 中 | 多档位 | ✅ 企业版可选独立 DB |

### 2.3 实现方式

```
每个请求 → API 网关解析 JWT → 提取 tenant_id → 透传给所有服务
                                                    │
MySQL: 所有表加 tenant_id 字段 + 联合索引
       SELECT * FROM documents WHERE tenant_id = ? AND ...
       
Milvus: 每个租户独立 Collection（向量库）
       → 数据物理隔离，检索快
       
Redis: Key 前缀 tenant_id:
       → tenant_123:query_cache:xxx
```

## 3. RAG Pipeline 详解

### 3.1 完整链路

```
[摄入端]                          [查询端]
                                  
文件上传 → 文档处理队列（Redis）    用户提问
    │                                    │
    ▼                                    ▼
格式解析 (PyMuPDF/python-docx)    Query 改写 (LLM)
    │                                    │
    ▼                                    ▼
智能切片 (500字/块, 200重叠)       混合检索
    │                               ├── 向量检索 (Milvus, Top 50)
    ▼                               └── 关键词检索 (MySQL FULLTEXT, Top 20)
Embedding (BGE-M3, 1024维)                │
    │                                    │
    ▼                                    ▼
写入 Milvus                      去重 + 合并 + 排序
(按 tenant_id 分 Collection)               │
                                           ▼
                                   Rerank (BGE-Reranker)
                                        │
                                        ▼
                                   Top 5 片段 → Prompt
                                        │
                                        ▼
                                   LLM 生成 (带约束)
                                   ├── 必须引用
                                   ├── JSON 格式输出
                                   └── 回答不足时说"不确定"
                                        │
                                        ▼
                                   答案校验 + 返回用户
```

### 3.2 切片策略决策

| 策略 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| 固定字数切 | 简单 | 切断语义 | 通用文档 |
| 按标题段落切 | 保留语义 | 段落长短不均 | 结构化文档 |
| 代码块保留 | 代码不被切 | 可能超长 | 技术文档 |
| 语义切分（Embedding 相似度） | 最精准 | 慢 3-5x | 长文档/专业文档 |

**我们的组合策略（平衡效果 vs 成本）：**
```
1. 优先按标题/段落切分
2. 代码块检测 → 保持完整
3. 超长段落 (> 800 字) → 按字数 + 保持句子完整来切
4. V1.0 暂不做 Embedding 语义切（成本考虑）
```

### 3.3 混合检索决策

| 维度 | 向量检索 | 关键词检索 |
|------|----------|------------|
| 擅长 | 语义相似（"请假"→"年假"） | 精确匹配（"401K"→"401K"） |
| 不擅长 | 数字/代码/专有名词 | 同义词/口语/模糊 |
| 我们的实现 | Milvus HNSW 索引 | MySQL FULLTEXT |
| 默认权重 | 60% | 40% |

## 4. 向量数据库选型

### 4.1 候选方案对比

| 维度 | Milvus | Pinecone | pgvector | Weaviate |
|------|--------|----------|----------|----------|
| 部署方式 | 自托管 / 云 | 纯 SaaS | 自托管（Postgres 扩展） | 自托管 / 云 |
| 数据量 | 亿级 | 亿级 | 千万级 | 亿级 |
| 查询延迟 | < 50ms | < 50ms | < 200ms | < 100ms |
| 多租户 | 需按 Collection 隔离 | 原生支持 | 需按 tenant_id 过滤 | 原生支持 |
| 成本 | 服务器 + 运维 | $70/月起 | 几乎免费（Postgres 自带） | 免费版 100 万向量 |
| 运维难度 | 中等 | 低 | 低 | 中等 |
| 适用规模 | 中大型 | 中大型 | 小型 | 中型 |

### 4.2 决策结论

**V1.0 选 Milvus**，理由：
1. 开源免费 + 自托管（数据不出企业 → SaaS 客户信任）
2. 性能强，亿级向量稳定
3. 多租户按 Collection 隔离，物理级安全
4. 国内社区活跃，坑少

**备选：**
- 如果 V1.0 客户量少 → 用 pgvector 过渡（零运维）
- 企业版私有化部署 → 必选 Milvus

## 5. LLM 网关设计

### 5.1 为什么要网关？
```
不做网关：前端直接调各 LLM API → 多个 SDK / 多个 Key / 计费混乱
做网关：所有 LLM 调用统一走网关 → 统一鉴权 / 统一计费 / 故障自动切换
```

### 5.2 网关能力

```
┌─────────────────────────────────────────────────┐
│                  LLM 网关                       │
│                                                 │
│  统一接口：/v1/chat/completions                  │
│                                                 │
│  ┌───────────┐  ┌───────────┐  ┌───────────┐   │
│  │ 路由策略  │  │ 计费      │  │ 故障转移  │   │
│  │ (模型/成本│  │ (token计数│  │ (API挂了   │   │
│  │  /租户)   │  │  /分租户) │  │  切备用)   │   │
│  └───────────┘  └───────────┘  └───────────┘   │
│                                                 │
│  ┌───────────┐  ┌───────────┐  ┌───────────┐   │
│  │ Prompt    │  │ 缓存      │  │ 限流      │   │
│  │ 管理      │  │ (相似查询 │  │ (防滥用   │   │
│  │ (版本化)   │  │  复用结果)│  │  按租户)   │   │
│  └───────────┘  └───────────┘  └───────────┘   │
│                                                 │
│  后端 LLM：GPT-4o-mini │ DeepSeek │ 通义千问     │
└─────────────────────────────────────────────────┘
```

### 5.3 成本控制策略

```
1. 路由策略：
   ├── 日常问答 → GPT-4o-mini（便宜）
   ├── 复杂推理 → 升级 GPT-4o（贵但准）
   └── 专业模式 → 用户付费升级才用

2. 缓存：
   ├── 相似问题（embedding cosine > 0.95）→ 直接返回缓存答案
   └── 高频问题 → 人工优化后预生成答案

3. Token 控制：
   ├── 检索片段截断（每个片段 ≤ 500 token）
   ├── System Prompt 压缩
   └── 答案限制长度（≤ 2000 token）
```

## 6. 计费模块设计

### 6.1 计费维度

```
┌──────────────────────────────────────────┐
│           套餐制 + 按量计费               │
│                                          │
│  固定费：订阅套餐（年度）                 │
│  ├── 基础版 ¥2,999/年  → 含 50K token    │
│  ├── 专业版 ¥8,999/年  → 含 200K token   │
│  └── 企业版 ¥29,999/年 → 含 1M token    │
│                                          │
│  超出部分：¥0.005 / 1K token（问答）      │
│  向量化：¥0.01 / 1K token（摄入）          │
│  API 调用：¥0.01 / 次                     │
└──────────────────────────────────────────┘
```

### 6.2 计费实现

```
每次调用 LLM → 记录 (tenant_id, model, input_tokens, output_tokens, timestamp)
                                      │
                                      ▼
                            异步汇总到 ClickHouse
                                      │
                                      ▼
                            每天凌晨结算 → 更新租户余额
                            → 余额不足 → 降级为只读（禁止问答）
                            → 余额耗尽 → 发邮件提醒续费
```

## 7. 可观测性（面试加分项）

```
指标（Metrics）— Prometheus
├── 系统层：CPU / 内存 / 网络 / 磁盘
├── 应用层：请求数 / 延迟 P95 / 错误率
├── 业务层：问答成功率 / 满意度 / Token 消耗
└── LLM 层：各模型调用次数 / 成本 / 超时率

日志（Logging）— ELK / Loki
├── 全链路 Trace ID（从用户请求到 LLM 返回）
├── QA 完整记录（Query / 检索结果 / Rerank / LLM 输入输出）
└── 错误分级（warn / error / critical）

链路追踪（Tracing）— Jaeger
└── 每个请求的耗时分解：Query改写→检索→Rerank→LLM→校验
    → 知道慢在哪里，优化什么
```

## 8. 技术选型汇总表

| 层 | 组件 | 选型 | 理由 |
|----|------|------|------|
| 前端 | 框架 | React + TypeScript | 生态好，类型安全 |
| 前端 | 样式 | TailwindCSS | 快速迭代，设计系统一致 |
| 前端 | 状态 | Zustand | 轻量，比 Redux 简单 |
| 网关 | API 网关 | APISIX | 开源，多租户 + 限流 + 插件多 |
| 后端 | 语言 | Go（知识库/计费）+ Python（RAG/Agent） | Go 高并发适合 CRUD，Python AI 生态强 |
| 后端 | 框架 | Gin（Go）+ FastAPI（Python） | 主流选择，社区好 |
| AI | Embedding | BGE-M3 | 中文效果好，1024 维，免费可自托管 |
| AI | Rerank | BGE-Reranker-V2 | 中文重排效果 SOTA |

| 向量 | DB | Milvus | 性能 + 多租户 + 自托管 |
| 关系 | DB | MySQL 8.0 | 成熟稳定，FULLTEXT 支持关键词检索 |
| 文件 | 存储 | MinIO | 开源 S3 兼容，自托管 |
| 缓存 | | Redis | 热点查询 + 队列 |
| 日志 | 分析 | ClickHouse | 列式存储，海量日志聚合极快 |
| 部署 | | K8s + Docker | 弹性伸缩，多租户隔离 |
| 监控 | | Prometheus + Grafana + Jaeger | 标准三件套 |
