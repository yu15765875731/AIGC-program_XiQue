# PRD 模板 — 通用产品需求文档

> 面试时被问"你怎么写 PRD"，用这份模板回答。3 年经验 vs 应届生的 PRD 区别：**不是写得更长，而是每个功能点都有决策依据**。

---

## PRD 标准结构（12 个章节）

```
1. 文档元信息
2. 背景与目标（为什么做）
3. 用户画像 & 使用场景（为谁做）
4. 范围界定（做什么 / 不做什么）
5. 功能需求（详细拆解 + 优先级）
6. 非功能性需求（性能/安全/兼容性）
7. 交互流程描述（用户旅程图 + 异常路径）
8. 数据实体说明（核心表结构 + 字段含义）
9. 指标与验收标准（怎么算做成了）
10. 依赖与风险（需要谁配合 / 什么坑）
11. 发布计划（分几期，每期交付什么）
12. 附录（竞品、调研、备选方案对比）
```

---

## 各章节填写要点

### 1. 文档元信息

| 字段 | 填写内容 |
|------|----------|
| 项目名称 | XXX 模块 PRD |
| 版本 | v1.0 |
| 负责人 | 产品经理名字 |
| 评审人 | 技术负责人 / UI / QA |
| 创建日期 | 2026-xx-xx |
| 最后更新 | 2026-xx-xx |
| 状态 | 草稿 / 评审中 / 已确认 / 已上线 |

### 2. 背景与目标

**3 年经验写法：**
```
❌ 应届生：「要做一个知识库，方便用户查资料」
✅ 3 年：  「客服团队重复回答率 60%，按 200 人规模估算，每年浪费
            约 1200 人时。做知识库后，目标重复率降到 20% 以下，
            QA 响应时间从 4 分钟降到 30 秒。」
```

### 3. 用户画像 & 使用场景

**3 年经验写法（用户故事格式）：**
```
作为 [新员工]，
我希望 [输入"报销流程"就能得到答案]，
以便 [不用找老同事要 SOP 文档]。
验收标准：答案必须带原文引用，支持一键跳转。
```

### 4. 范围界定（重要！体现控制力）

```
本期要做（In Scope）：
- 上传 PDF/Word/Markdown 自动处理
- 单轮 + 多轮问答
- 👍👎 反馈

本期不做（Out of Scope）：
- 上传后立即可见（需要处理时间 1-5 分钟）
- 图像识别（PDF 里的图不处理）
- 多人同时编辑知识库文档
```

### 5. 功能需求（核心章节）

**每个功能点必须包含：**
- 功能描述
- 用户故事
- 交互说明（关键状态：空状态 / 加载中 / 成功 / 失败）
- 优先级（P0 = 必须做 / P1 = 应该做 / P2 = 可以做）
- 决策依据（为什么这样设计，备选方案是什么）

### 6. 非功能性需求

```
性能：单次问答 P95 响应时间 < 3s（不包括 LLM 生成）
可用性：99.9% 在线（月停机 < 43 分钟）
安全：所有客户数据加密存储，支持 SOC 2 审计
兼容性：Chrome 120+ / Edge 120+ / Safari 17+
```

### 7. 交互流程描述

**要覆盖正常路径 + 所有异常路径：**
```
正常路径：上传 → 处理中 → 处理完成 ✓
异常路径1：上传失败（网络中断）→ 提示重试
异常路径2：文档格式不支持 → 提示不支持类型 + 支持列表
异常路径3：文档内容为空 → 提示"未识别到有效文本"
异常路径4：单个文件 > 50MB → 提示超限 + 建议拆分
```

### 8. 数据实体说明

**3 年经验写法（核心字段 + 含义）：**
```
知识库（KnowledgeBase）
├── id: 主键
├── name: 名称
├── description: 描述
├── embedding_model: 使用的向量化模型（影响后续效果）
├── index_type: 索引类型（HNSW / IVF，影响检索速度 vs 准确率）
├── created_by: 创建人
├── member_count: 成员数
├── usage_stats: 近 30 天问答次数
└── last_updated_at: 最后更新时间

文档（Document）
├── id: 主键
├── kb_id: 所属知识库
├── source_type: 来源（upload / url / api / sync）
├── file_name: 原始文件名
├── file_size: 文件大小
├── content_hash: 内容 hash（用于增量更新）
├── status: 处理状态（pending / processing / done / failed）
├── chunk_count: 切分后的片段数
└── failed_reason: 失败原因（供用户排查）

问答记录（QA）
├── id: 主键
├── user_id: 提问人
├── kb_ids: 关联的知识库（支持多库检索）
├── question: 原始问题
├── rewritten_question: 改写后的问题（用于检索）
├── answer: 生成的答案
├── sources: 引用的片段列表 [{doc_id, chunk_id, score}]
├── feedback: 👍 / 👎 / null
├── tokens_used: 消耗的 token 数（计费用）
└── latency_ms: 总耗时
```

### 9. 指标与验收标准

```
知识库管理模块验收：
[ ] 上传 1 份 10MB PDF，5 分钟内处理完成
[ ] 处理完成后，搜索关键字能命中原文
[ ] 失败文档能看到明确失败原因
[ ] 文件 > 50MB 会拦截并提示
[ ] 处理进度实时可查
```

### 10. 依赖与风险

```
依赖：
- 向量数据库 Milvus 集群稳定可用
- LLM API 响应正常（P95 < 2s）

风险：
- LLM 幻觉 → 所有答案必须带引用链接，用户可一键验证
- 向量化成本 → 预计算 + 缓存常用查询结果
```

### 11. 发布计划

```
V1.0（月 1）：核心链路上线 — 单库上传 + 单轮问答
V1.5（月 2）：多库检索 + 多轮上下文 + 👍👎 反馈
V2.0（月 3）：Agent 工作流 + API 开放
```

### 12. 附录

- 竞品功能对比表
- 用户调研摘要（3 个典型反馈）
- 备选方案对比（如"为什么选 Milvus 而不是 Pinecone"）
