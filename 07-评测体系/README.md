# 评测体系（Eval）

> **这是整个项目里含金量最高的一份东西。**
> 文档写得再漂亮，也回答不了一句「你怎么知道它答得准」。
> 有评测集 + 真实数字，你和其他候选人就不在同一个层次上。

---

## 0. 一句话说清「评测」是干什么的

**评测 = 用一套固定的标准题目，反复给系统考试，把「感觉变好了」变成「数字变好了」。**

没有评测会发生什么：

```
产品经理：这次改完效果好多了！
面试官：  怎么个好法？
产品经理：感觉回答更准了……
面试官：  （结束）
```

有了评测：

```
产品经理：我把 Top-1 抽取改成 Top-3 拼接，在自建 100 条评测集上，
          答案要点覆盖率从 0.863 提升到 0.875，幻觉率保持不变。
面试官：  这个数据集是怎么设计的？
产品经理：四类题……（见下）
面试官：  （这个人是真的做过）
```

## 1. 指标定义

### 1.1 效果指标（回答「答得对不对」）

| 指标 | 定义 | 计算方式 | 面向谁 |
|------|------|---------|--------|
| **检索 Hit@K** | 期望来源是否落入 Top-K 召回 | 期望文档 ∈ 召回文档集 → 1 | 定位「找不到」类问题 |
| **要点召回率** | 期望要点在召回片段中出现的比例 | 命中要点组数 / 总要点组数 | 定位「找得不全」 |
| **答案要点覆盖率** | 期望要点在最终答案中出现的比例 | 命中要点组数 / 总要点组数 | ⭐ 最核心的效果指标 |
| **答案正确率** | 要点覆盖率 ≥ 阈值的题目占比 | 默认阈值 0.6 | 汇报用主指标 |
| **拒答准确率** | 不可答题中「正确说不知道」的比例 | 正确拒答数 / 不可答题数 | ⭐ 企业信任度 |
| **幻觉率** | 不可答题中「硬答」的比例 | 1 − 拒答准确率 | ⭐⭐ 企业最怕这个 |
| **引用率** | 回答附带来源的比例 | 有来源的回答数 / 总回答数 | 可验证性 |

### 1.2 体验与工程指标

| 指标 | 说明 |
|------|------|
| P50 / P95 延迟 | 用户感知的快慢。P95 比平均值重要得多 |
| 解析失败率 | LLM 输出不是合法 JSON 的比例 |
| 服务可用性 | 接口成功率 |
| 单次 Token 成本 | 入 Token × 单价 + 出 Token × 单价 |

### 1.3 指标之间的关系（面试常被追问）

```
要点召回率低   → 检索没找全 → 改切片 / 检索策略 / 补文档
要点召回率高但覆盖率低 → 找到了但没用上 → 改 Prompt / 改上下文组装 / 换模型
幻觉率高       → 拒答阈值太低 或 缺语义检索 → 标定阈值 / 上向量检索
```

**这就是「归因」**。你不是看到数字低就调 Prompt —— 不同原因对应完全不同的动作。

## 2. 评测集设计：四类题

**只测「正常题」的评测集等于没有评测。** 企业真正怕的是编造，所以要四类都覆盖。

| 类型 | 数量 | 出题方式 | 考察什么 | 期望行为 |
|------|------|---------|---------|---------|
| **正常题** | 60 | 答案明确在文档某处 | 基本能力 | 答对 |
| **边界题** | 20 | 需要组合 2 条规则 / 判断阈值 / 排除错误前提 | 推理能力 | 答对 |
| **异常题** | 15 | 文档里**没有**的，或其他主题 | ⭐ 会说「不知道」 | 拒答 |
| **对抗题** | 5 | 越界任务、隐私、协助违规 | ⭐ 守住边界 | 拒答 + 说明 |

### 出题 SOP（照着做就行）

```
第 1 步  挑 20 道正常题，**手写标准答案**（不要复制文档，要写「答案」）
第 2 步  每道题写下：答案在哪个文档 → expected_sources
                    答案必须包含哪几个要点 → expected_keywords
第 3 步  出 15 道「文档里查不到」的题 —— 技巧是选**同一主题但细节缺失**的
        （如：文档写了"转专业条件"，你就问"转专业要交多少学费"）
        ⭐ 这类题最能暴露问题，也最能证明你的产品水平
第 4 步  出 5 道对抗题（越界/隐私/协助违规）
第 5 步  出 20 道边界题 —— 技巧是「把两条规则拼在一起问」
        （如：请假 5 天要找谁审核？→ 需要先查区间表）
第 6 步  扩充到 100 条，冻结版本，之后只增不改（否则数据会泄露到调优里）
```

### 数据集分层（专业做法，面试加分）

| 分层 | 用途 | 纪律 |
|------|------|------|
| **开发集** | 调 Prompt、调检索参数 | 可以反复看 |
| **验证集** | 选参数 | 看的次数要少 |
| **测试集** | 冻结，只看最终结果 | 调优期间**不许看** |

> 为什么？因为你在开发集上反复调参，会「过拟合到开发集」。
> 真实表现要用一个你从没看过的测试集去验。

## 3. 字段说明（`eval_set_demo.csv`）

| 字段 | 说明 | 示例 |
|------|------|------|
| `id` | 题号。前缀标识类别：N / B / U / A | `N01` |
| `category` | `normal` / `boundary` / `unanswerable` / `adversarial` | `boundary` |
| `question` | 用户会怎么问（**用口语，别用文档里的书面语**） | `请假两天找谁审批` |
| `expected_answer` | 人工写的标准答案要点 | `学院分管学生工作负责人` |
| `expected_sources` | 应命中的文档名，多个用 `\|` 分隔 | `学籍与考勤管理规定` |
| `expected_keywords` | 必须出现的关键要点。`\|` 分组，组内 `/` 表示同义表达任一命中即可 | `85分/前10%\|综合素质测评` |
| `answerable` | `yes` / `no`。`no` 表示期望系统拒答 | `no` |
| `risk_level` | `low` / `medium` / `high` | `medium` |
| `notes` | 出题意图（写给自己和面试官看） | `需要先判断时长落在哪个区间` |

**`expected_keywords` 是评测的灵魂。** 它决定了「什么叫答对」。写得越松越容易自欺，写得越紧越容易误杀。

## 5. 实测基线（示例语料 · 100 条题 · 24 个片段）

> 这些数字是我在你机器上真跑出来的，**不是编的**。语料换成你的文档后必须重跑。

| 配置 | 答案正确率 | 要点覆盖率 | 拒答准确率 | 幻觉率 |
|------|-----------|-----------|-----------|--------|
| BM25 Top-1，**不设拒答阈值** | 93.8% | 0.938 | 0% | **100%** |
| **BM25 Top-1 + 阈值** ← V0 基线 | **86.2%** | 0.863 | **90.0%** | **10.0%** |
| BM25 Top-3 拼接 | 87.5% | 0.875 | 90.0% | 10.0% |
| BM25 Top-1 + jieba 分词 | 68.8% | 0.688 | 90.0% | 10.0% |

### 从这张表能读出 4 个结论（面试直接讲）

1. **不设阈值时正确率最高（93.8%），但幻觉率 100%** —— 它把所有问题都硬答了。
   对内部知识助手来说，一个「自信地给出错误制度」的助手比「说不知道」的助手危险得多。
   → **这就是为什么企业产品必须设拒答阈值，也是为什么「正确率」不能当唯一指标。**

2. **加阈值后正确率降到 86.2%，幻觉率降到 10.0%** —— 用 7.6 个百分点的正确率换来 90 个百分点的幻觉率下降。
   这笔交易值不值？取决于业务风险。这就是**产品决策**，不是技术决策。

3. **jieba 分词反而让正确率从 86.2% 掉到 68.8%** —— 反直觉，但可复现。
   → 教训：**不要迷信「更专业的工具」，要用评测集说话。** 换语料后请自己重跑。

4. **幻觉率卡在 10.0% 就下不去了** —— 剩下的 2 道题（如「图书馆一共有多少册藏书」「毕业设计查重率是多少」）
   在纯关键词检索下的得分比很多**可答题还高**（因为「图书馆」「毕业设计」这些词高度重合）。
   → **纯靠调阈值已经无解，必须上语义检索/混合检索。** 这是升级到 V1 的硬证据，不是拍脑袋。

## 6. 三个必须知道的坑（都是我踩过的）

### 坑 1：文档写「提前 1 天」，评测要点写「提前1天」→ 明明答对了却判错

**症状**：要点覆盖率异常低，但肉眼看答案是对的。

**原因**：中文文档里数字两侧常有空格，匹配时不去空格，测的就是排版而不是能力。

**解法**：比对前做文本归一化（去空格、统一全半角）。`evaluate.py` 里的 `normalize()` 就是干这个的。

> ⚠️ 这个坑一开始让我的全部指标都虚低了一半。**如果你发现指标低得离谱，先去查评测集本身。**

### 坑 2：CSV 里混进一个半角逗号 → 整行错位，静默算错

**症状**：某个类别的题量对不上（应该 20 条却算成 21 条）。

**解法**：写完 CSV 后校验字段数：

```powershell
@'
import csv
from pathlib import Path
p = next(Path("../../").glob("07-*/eval_set_demo.csv"))
rows = list(csv.reader(p.read_text(encoding="utf-8").splitlines()))
for i, r in enumerate(rows[1:], 1):
    if len(r) != len(rows[0]):
        print("BAD ROW", i, len(r), r)
'@ | .\.venv\Scripts\python.exe -
```

### 坑 3：语料太小 → 指标虚高

当前示例语料只有 **24 个片段**，Top-5 就占了 21%。Hit@K 几乎必然 100%，这个指标在这个规模下没有区分度。

**解法**：语料扩到 50 个片段以上再看 Hit@K。或者干脆看**要点覆盖率**——它在小语料上也有效。

## 7. 数据闭环：从 👎 到「下周改什么」

评测集是「离线的考卷」，线上反馈是「真实的考卷」。两者要接起来：

```
用户 👎
  └─ 弹窗收集原因（多选）
       ├─ 答案不正确
       ├─ 答案不完整
       ├─ 格式不好读
       └─ 引用不对
                │
                ▼
        每周离线归因（不是实时处理 —— 降成本、保稳定）
                │
        ┌───────┼────────┬──────────────┐
        ▼       ▼        ▼              ▼
     检索失败  生成错误  知识缺失      格式问题
        │       │        │              │
     改切片/   改Prompt/ 补文档/       改渲染/
     上混合    加示例    催内容负责人   调模板
     检索
                │
                ▼
        把高频 Bad Case **反向加进评测集**
                │
                ▼
        跑回归 → 确认没把别的题改坏 → 灰度发布
```

> **关键洞察**：不是所有问题都靠调 Prompt 解决。
> 我最多的 Bad Case 归因是「检索失败」和「知识缺失」——这两个调 Prompt 一点用都没有。
> 说得出这句话，就说明你不是只会「调提示词」的 PM。

### 换成你自己的文档时要改什么

1. 把 `08-V0原型/local_rag/data/docs/` 换成你的真实文档（学生手册 / 公司制度 / 产品手册）
2. 重新跑 `ingest.py` 建索引
3. 按第 2 节 SOP 重写 `eval_set.csv`（**至少 60 条正常题 + 15 条查不到的题**）
4. 重新跑 `calibrate.py` 标定阈值（语料一变，分数分布全变）
5. 跑 `evaluate.py`，得到**你自己的**真实数字
6. 把数字填进 [06-实战方案](../06-实战方案/README.md) 第 8 节的简历文案
