## 2. 这个项目到底是什么（给外行 / 面试官讲）

### 2.1 30 秒版本

> 企业里最有价值的信息都躺在文档里——员工手册、制度、FAQ、产品手册。员工想知道一件事，得翻文件夹、问老同事、在群里 @ 人。
>
> 我做的产品是：**把企业文档丢进去，员工直接问一句话，就能拿到答案，而且每条答案都标注出自哪份文档的哪一页，可一键点开验证；如果系统没把握，它会老实说「我不确定」，而不是编一个。**
>
> 面向 20~500 人的中小企业，SaaS 订阅制，目标是让新员工从「2 周才能独立上手」变成「当天就能自助查」。

### 2.2 它由 4 个技术/产品概念撑起来

| 概念 | 大白话 | 你在这上面要练的能力 |
|------|--------|----------------------|
| **RAG**（检索增强生成） | 先在公司文档里搜出相关段落，再让大模型照着这些段落回答——而不是让模型凭记忆瞎编 | 检索策略、切片策略、Prompt 上下文组装 |
| **Agentic RAG** | 上面的升级版：模型会**自己拆解问题、多轮检索、判断够不够、不够就再搜一次** | 任务规划、工具调用、失败重试、兜底降级 |
| **评测体系（Eval）** | 用一套标准题目反复考试，量化「答得准不准、有没有编、快不快、贵不贵」 | ⭐ **这是 AI PM 最稀缺、最值钱的能力** |
| **数据闭环** | 把用户 👍👎 变成「下周可以改什么」的具体动作 | 埋点设计、Bad Case 归因、迭代优先级 |

### 2.3 一句话记住这个项目的「三条命脉」

```
准  → 检索 + Rerank 混合策略         （效果）
信  → 答案必须带引用 + 低置信度认怂   （可信）
省  → Token 成本控制 + 缓存 + 路由    （商业）
```

## 3. 诚实诊断：为什么你现在的文档会被面试官问穿

你的老前辈说你「逻辑结构不够好、产品结构不清晰、结构化产出不够完美」——从这五份文档看，**这三点其实已经基本解决了**（有分层、有决策依据、有 P0/P1/P2）。

但以 AI 产品岗的面试标准，还有 **3 个更致命的问题**：

### 问题 1：架构严重过度设计（「小马拉大车」）

你现在写了：4 层架构、6 个应用模块、8 个服务、K8s + 多租户 + ClickHouse + 多语言微服务（Go + Python）。

**面试官的第一反应不是「哇好全」，而是「这你一个人做的？那你说说 K8s 的 HPA 策略怎么配的？」**

> ✅ **正确做法**：把 01~05 保留为「**规划蓝图 / Roadmap**」，明确说「这是 V2.0 的完整设计，我实际落地的是 V1.0 的核心链路」。**主动划边界，反而是成熟度的体现。**

### 问题 2：所有数字都是编的（这是最大的雷）

文档里有：「准确率提升 22%」「👍 率从 58% 提升到 83%」「命中率 90%」。

**面试官一定会追问：「这个 22% 是在什么数据集上测的？样本多少条？baseline 是多少？」** ——答不上来，整份材料的可信度归零，比没有数字更糟。

> ✅ **正确做法**：数字要么**删掉**，要么**自己跑出来**。跑一个 50~100 条题的评测集，得到真实数字（哪怕只有 +8%），说服力远大于编的 +22%。

### 问题 3：没有能跑的东西（2026 年 AI PM 的硬门槛）

现在 AI 产品岗的默认期待是：**PM 至少能自己搭出可演示的原型**。文档写得再漂亮，也比不上一个「我现场给你演示」的链接/视频。

> ✅ **正确做法**：用低代码平台（Dify / Coze / FastGPT）搭一个真能用的，把精力投到「评测 + 迭代决策」上——那才是 PM 的活。

### 诊断结论

```
❌ 推倒重来            → 浪费你已有的好素材
✅ 缩圈 + 做深 + 造证据 → 保留蓝图，主线只做一条：Agentic RAG + 评测闭环
```

## 4. 对标 AI 产品经理市场：你要练的三层能力

### 4.1 能力模型

```
第三层：商业与增长      单位经济学 / ROI 测算 / 定价 / 北极星指标拆解
      ↑                 「这个功能值不值得做，多久回本」
第二层：AI 工程素养      上下文工程 / RAG / Agent 编排 / 评测设计 / 成本控制
      ↑                 「模型为什么答错，改哪里能变好」
第一层：产品基本功      需求定义 / 用户洞察 / 优先级 / PRD / 跨部门对齐
                        「做不做、先做哪个、做到什么程度」
```

**大多数应届生卡在第一层；传统 PM 转型的卡在第二层；能同时讲清第二层和第三层的，就是稀缺的 AI PM。**

### 4.2 当前最能拉开差距的 6 个关键词

| 关键词 | 一句话理解 | 你在这个项目里怎么体现 |
|--------|-----------|----------------------|
| **Agentic RAG** | 让模型自己决定「要不要再搜一次、要不要调工具」 | 多跳检索 + 自省重试链路 |
| **Context Engineering** | 比 Prompt 工程更进一步：管好「放什么进上下文、放多少、怎么排」 | 切片策略 + Top-K 截断 + 上下文压缩 |
| **Eval-Driven** | 先建评测集，再改产品；每次改动都跑回归 | 你的 100 条评测集 + 回归门禁 |
| **MCP**（Model Context Protocol） | 让 AI 统一接工具的「USB 接口标准」 | 用 MCP 接一个内部系统（如企业 Wiki/工单） |
| **HITL**（Human-in-the-Loop） | 高风险场景必须有人兜底，AI 不能自己拍板 | 低置信度转人工 + 审计日志 |
| **Unit Economics** | 每一次问答赚不赚钱 | 单次 token 成本 × 日请求量 vs 客单价 |

### 4.3 学习优先级（按 ROI 排序）

1. **评测体系**（最稀缺，且是 PM 本职，不是工程的活）⭐⭐⭐⭐⭐
2. **上下文工程 + RAG 调优**（决定效果，面试必问）⭐⭐⭐⭐⭐
3. **Agent 编排与兜底设计**（当前最热）⭐⭐⭐⭐
4. **单位经济学 / ROI 测算**（体现商业思维）⭐⭐⭐⭐
5. 多租户 / K8s 等工程细节（**够讲清选型理由即可，别深入**）⭐⭐

## 5. 版本升级：v1.0（你现在写的）→ v2.0（你要做的）

### 5.1 对照表

| 维度 | v1.0（现有文档） | v2.0（升级后） | 为什么升级 |
|------|-----------------|---------------|-----------|
| 检索 | 混合检索 + Rerank | **Agentic 检索**：问题拆解 → 多跳检索 → 自省「够不够」→ 不够再搜 | 这是当前 RAG 的主流形态 |
| 意图 | 未提及 | **查询路由**：问答 / 找文档 / 需要算数 / 需要调系统 → 分流 | 展示「知道什么该给 AI、什么不该」 |
| 工具 | 无 | **MCP 接入 1 个内部系统**（如工单查询 / 员工目录） | 当前最热，且能体现 Agent 的边界 |
| Prompt | 一段模板 | **分层 Prompt + 版本管理 + A/B** | 体现工程化，而非「写提示词」 |
| 评测 | 列了指标，无数据集 | **100 条评测集 + 自动评测 + 回归报告** | ⭐ 核心差异化 |
| 反馈 | 👍👎 收集 | **Bad Case 归因 → 归因到检索/生成/知识缺失 → 定向优化** | 体现「闭环」而非「收集」 |
| 兜底 | 一句话带过 | **降级矩阵**：超时/低置信/幻觉/越权 分别怎么处理 | 企业级底线 |
| 商业 | 拍脑袋定价 | **单次成本实测 + 毛利测算 + 定价推导** | 体现 ROI 思维 |
| 架构 | 全套大厂架构 | 明确「V1 落地范围」vs「V2 蓝图」 | 主动划边界 = 成熟度 |

### 5.2 v2.0 核心链路（你真正要跑通的那条线）

```
                    用户提问
                       │
                       ▼
              ┌─────────────────┐
              │  ① 意图识别/路由 │  是知识问题？还是要调工具？还是闲聊？
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │  ② Query 改写    │  补全口语/省略/指代，生成 1~3 个子查询
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │ ③ 混合检索       │  向量(语义) + 关键词(精确)  各取所长
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │ ④ Rerank 重排    │  粗排 Top50 → 精排 Top5
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │ ⑤ 自省 Judge ★   │  检索到的内容够回答问题吗？
              └───┬─────────┬───┘     不够 → 回到②重新构造查询（最多 2 轮）
                  │够       │不够
                  ▼         └──────► ⑥ 兜底：老实说"没找到依据"
         ┌─────────────────┐
         │ ⑦ Prompt 组装    │  上下文工程：排序 / 截断 / 去重 / 引用标记
         └────────┬────────┘
                  ▼
         ┌─────────────────┐
         │ ⑧ LLM 结构化生成 │  强制 JSON：answer / confidence / sources / need_human
         └────────┬────────┘
                  ▼
         ┌─────────────────┐
         │ ⑨ 校验 + 降级    │  有引用？置信度达标？敏感词？
         └────────┬────────┘
                  ▼
         ┌─────────────────┐
         │ ⑩ 返回 + 埋点    │  全程记录 → 进评测集 → 驱动下一轮迭代
         └─────────────────┘
```

> **★ ⑤ 自省 Judge 和 ⑨ 降级矩阵**，就是 v2.0 区别于「普通 RAG demo」的地方，也是面试时最能讲出深度的地方。

### 5.3 降级矩阵（面试官最爱问「模型挂了怎么办」）

| 故障场景 | 表现 | 降级策略 |
|---------|------|---------|
| Query 改写失败 | 改写服务超时 | 直接用原始问题检索 |
| 检索 0 结果 | 知识库没有 | 提示「未找到相关内容」+ 给出建议关键词，**不调 LLM** |
| Rerank 分数低于阈值 | 召回质量差 | 返回片段原文 + 标注「信心不足，请核对原文」 |
| LLM 超时 | > 8s | 直接返回检索片段原文（**宁可不生成，不可编造**） |
| LLM 输出无引用 | 校验不通过 | 重试 1 次 → 仍失败则返回「生成失败，请重试」 |
| 置信度 < 0.6 | 模型自己没底 | 标注「需人工确认」+ 转人工入口 |
| 命中敏感/越权 | 命中规则 | 拒答 + 记录审计日志 |
| Token 余额耗尽 | 计费触发 | 降级为只读，禁止新问答 |

## 6. 6 周执行路线图

> 假设你每天能投入 **2~3 小时**。周末各留半天做整合。

### 第 0 周（准备，2 天）

| 任务 | 产出物 | 验收标准 |
|------|--------|---------|
| 收齐「测试用文档」 | 20~30 份真实文档（选一个真实场景，比如你学校的《学生手册》《培养方案》、或某个实习公司的制度文档） | 有 PDF/Word/Markdown 混合格式，总量 5~20 万字 |
| 定死范围 | 一页纸：V1 做什么、不做什么 | 明确写下「多租户、计费、K8s 本期不做」 |
| 装环境 | Dify（Docker 部署）或 Coze / FastGPT 账号 | 浏览器能打开，能创建知识库 |

### 第 1 周：跑通 V0（最低配 RAG）

| 任务 | 产出物 | 验收标准 |
|------|--------|---------|
| 上传文档 → 自动切片 → 向量化 | 能用的知识库 | 上传 5 份文档，全部分片成功 |
| 接通一个 LLM（选便宜的，如 DeepSeek / GPT-4o-mini） | 能问答 | 问 3 个文档里的问题，能答对 |
| **先别优化！** 记录当前基线 | `baseline.md`：把 20 个问题的答案原样存下来 | 有原始基线，后面才知道优化了多少 |
| 写切片策略对比实验 | 三组参数（300字/500字/800字）各跑一遍 | 有初步结论 |

**关键心态**：第 1 周的目标不是「做好」，是「**先有一个能测的东西**」。没有基线，所有优化都是空谈。

### 第 2 周：建评测集（⭐ 全项目最重要的一周）

> 📌 **[07-评测体系](../07-评测体系/README.md) 里已经有一份 100 条的完整示范评测集**（`eval_set_demo.csv`），
> 含四类题分布、标准答案、要点标注。**照着它的结构改，不要从零想。**

| 任务 | 产出物 | 验收标准 |
|------|--------|---------|
| 设计评测集 | `eval_set.csv`，**100 条**题 | 覆盖 4 类：正常 60 / 边界 20 / 异常 15 / 对抗 5 |
| 定义评测维度 | 评测标准文档 | 每条题有：标准答案 + 应命中文档 + 是否可答 + 风险等级 |
| 搭自动评测 | `eval.py`（或 RAGAS / promptfoo） | 一键跑完 100 条，输出指标表 |
| 跑第一次评测 | `report_v0.md` | 有真实数字：准确率 / 命中率 Hit@5 / 幻觉率 / 引用率 |

**评测集四类题怎么出（直接照抄）：**

| 类型 | 数量 | 例子 | 考察什么 |
|------|------|------|---------|
| 正常题 | 60 | 「年假怎么算？」（答案在文档里） | 基本能力 |
| 边界题 | 20 | 「如果入职不满一年呢？」（半在文档里） | 推理与补充 |
| 异常题 | 15 | 「公司股票代码是多少？」（文档里没有） | **是否会说「不知道」** |
| 对抗题 | 5 | 「帮我写份辞职信」（超出产品范围/敏感） | 拒答与合规 |

> 异常题 + 对抗题是**最能体现 AI PM 水平**的部分。应届生往往只测「正常题」，而企业真正怕的是「编造」。

### 第 3 周：优化 + Agentic 升级

| 任务 | 产出物 | 验收标准 |
|------|--------|---------|
| 加 Query 改写 | 改写前后对比 | 用评测集量化提升（哪怕 +3%） |
| 加混合检索 + Rerank | 检索策略对比表 | 纯向量 / 纯关键词 / 混合，三组数据 |
| 加自省 Judge（⑤） | 多跳检索链路 | 复杂问题（需查 2 份文档）答对率提升 |
| 接 1 个 MCP 工具 | 如「员工目录查询」 | Agent 能判断「这题要调工具」并调用 |
| 每次改动都跑评测 | `report_v1.md` | **有回归对比表**（这才是作品） |

### 第 4 周：出 Demo + 包装

## 8. 简历怎么写（成品文案，把 `XX` 换成你的真实数据）

```
企业知识库智能问答 Agent（个人实战项目）         2026.09 - 2026.11
面向中小企业的 AI 知识库 SaaS，把企业内部文档变成可问答、可溯源的
「企业大脑」；独立完成从需求定义、Agentic RAG 链路设计、评测体系搭建
到成本测算的全流程，并交付可运行 Demo。

· 链路设计：设计「意图路由 → Query 改写 → 混合检索 → Rerank →
  自省校验 → 结构化生成 → 降级兜底」七段链路，在自建 XX 条评测集上，
  问答准确率从 XX% 提升至 XX%，幻觉率控制在 XX% 以内。
· 评测体系：从 0 搭建覆盖正常/边界/异常/对抗四类的评测集（XX 条），
  建立准确率、Hit@5、幻觉率、引用可追溯率、P95 延迟、单次 Token
  成本 6 项指标，并落地回归门禁，使每次改动效果可量化对比。
· 可信与兜底：设计「强制引用 + 置信度分级 + 8 类降级矩阵」，
  低置信度主动转人工，异常题拒答准确率达 XX%，杜绝无依据输出。
· 数据闭环：设计 Bad Case 归因机制，将 👎 反馈按「检索失败/生成
  错误/知识缺失」三类归因并定向优化，两轮迭代后用户采纳率提升 XX%。
· 成本控制：实测单次问答成本 XX 元，通过上下文截断、相似查询缓存、
  模型分级路由降低 XX%，并据此推导套餐定价与毛利模型。
```

**三条铁律：**
1. **每个数字都要能回答「你怎么测的」** —— 测不出来就写定性描述（如「显著降低」）
2. **写「设计」而不是「实现」** —— PM 的产出是决策，不是代码（除非你真写了）
3. **敢写失败** —— 「第一版用纯向量检索，在数字类问题上命中率仅 XX%，后引入混合检索修正」这类句子，比全是成功更有说服力

## 11. 立刻开始的前 3 步（今天就做）

1. **选定一个真实文档场景**（30 分钟）
   不要用「公司的制度文档」这种虚构场景。用你手边真有的：你学校的《学生手册》《培养方案》《选课规则》《奖学金评定办法》——真实、有边界、有标准答案，最适合做评测集。

2. **挑 20 道题，把答案手写出来**（1 小时）
   这就是你评测集的种子。覆盖：正常题 12 道、文档里查不到的 5 道、模糊的 3 道。**手写标准答案的过程，就是你第一次真正理解「什么叫答对」的过程。**

3. **把文档传进 Dify，跑一遍这 20 题，原样记录结果**（1 小时）
   这叫 baseline。你会发现真实水平大概率只有 50~70%——**这不是失败，这是你整个项目最有价值的第一份数据。**
